# Collecting-resource experiment

The `marlkit.collectingresource` experiment studies multi-agent resource collection in a spatial environment. Agents request resources from production units, receive collection rewards, and pay a distance-dependent penalty. The same environment and scenario can be combined with different reward models to study the effect of reward design on learned behavior.

This README documents the implementation behind the generic MARLKIT launcher. The launcher menu discovers the concrete classes in `marlkit.collectingresource.launchers` from their runtime metadata and uses the headings below for documentation navigation.

## Quick start

From the repository root, build and launch the generic experiment menu:

```bash
./gradlew :MLK-experiments:run
```

Select **Collecting-resource experiments**, choose one of the four reward-model launchers, and press **Launch selected experiment**. Each simulation starts in a separate JVM, leaving the menu available for additional launches.

The concrete launcher classes can also be started directly from an IDE or from the generated distribution. Their default `main` methods start MaDKit with INFO-level logging and the standard simulation startup sequence.

## Available launchers

All four launchers extend `LauncherCollectingResource`. They use the same scheduler, environment dimensions, agent implementation, and scenario; only the reward model changes.

### Fully Cooperative Reward

`LauncherFullyCooperativeReward` uses `FullyCooperativeReward`. Every agent receives the average raw reward generated by all agents during a step, encouraging collective performance.

**Launcher:** `LauncherFullyCooperativeReward`

### Mixed Reward

`LauncherMixedReward` uses `MixedReward`. Each agent receives the reward generated from its own reaction events, so agents optimize their individual outcomes.

**Launcher:** `LauncherMixedReward`

### Fair Mixed Reward

`LauncherFairMixedReward` uses `FairMixedReward(0.5)`. Each individual reward is mixed with the lowest raw reward observed during the step, adding an equity term to the individual objective.

**Launcher:** `LauncherFairMixedReward`

### Logistical Reward

`LauncherLogisticalReward` uses `LogisticalRewardModel(1.0)`. Collection rewards are scaled according to the available stock and the number of agents requesting the same production unit.

**Launcher:** `LauncherLogisticalReward`

## Experiment architecture

The package follows the standard MARLKIT experiment composition:

| Component | Implementation | Responsibility |
|---|---|---|
| Launcher base | `launchers.LauncherCollectingResource` | Connects the scheduler, model, viewer, environment, scenario, and reward model. |
| Environment | `environment.EnvCollectingResource` | Processes resource requests, allocates stock, creates collection events, and applies distance penalties. |
| State | `environment.StateUnites2D` | Stores production units, stocks, agent positions, and spatial state. |
| Agent | `agent.CollectingResourceAgent` | Creates one resource-request action per production unit and configures Q-learning. |
| Scenario | `scenario.ScenarioSpatial5` | Creates six production units and three initial agent positions on a 10 × 10 environment. |
| Scheduler | `scheduler.SchedulerCollectingResource` | Defines episode duration, display timing, evaluation, and simulation limits. |
| Viewer | `viewer.ViewerCollectingResource` | Displays the spatial production units, resources, agents, and environment state. |
| Evaluator | `systemevaluator.CollectingResourceEnvEvaluator` | Records total reward, lowest agent reward, and the number of resources acquired. |

The launcher hierarchy is:

```text
LauncherCollectingResource
├── LauncherFullyCooperativeReward  -> FullyCooperativeReward
├── LauncherMixedReward             -> MixedReward
├── LauncherFairMixedReward         -> FairMixedReward(0.5)
└── LauncherLogisticalReward        -> LogisticalRewardModel(1.0)
```

## Environment and scenario

`LauncherCollectingResource` creates an `EnvCollectingResource` with width `10` and height `10`. The scenario creates three agents and six spatial production units:

| Resource type | Position(s) | Base price |
|---|---|---:|
| A | `(5, 4)` | `30` |
| B | `(5, 5)` | `5` |
| C | `(5, 6)` | `3` |
| D | `(3, 4)`, `(3, 5)`, `(3, 6)` | `0` |

Each agent requests one production unit per step. The environment groups requests by unit, processes the available stock, and emits a `CollectResourceEvent2D` when an agent receives a resource. It also emits a `DistancePenaltyEvent` based on the distance between the agent and the requested unit.

The scenario configuration is implemented by `ScenarioSpatial5`:

- three agents start at `(4, 4)`, `(4, 5)`, and `(4, 6)`;
- resource units have deterministic initial stock in the current configuration;
- the distance penalty is `0.5` per spatial unit;
- each request asks for one resource unit.

## Other modules configuration

All components except the reward model are identical across experiments. 

Training and execution are completely decentralized (DTE). There is no communication between agents, and agents do not build or use models of other agents.

## Agents and learning

`CollectingResourceAgent` uses one discrete action for every production unit in the scenario. 

| Setting | Value |
|---|---|
| Action space | One `ActionRequestResource` per production unit |
| Policy | `QValueBasedPolicy` |
| Initial exploration parameter | `1.0` |
| Exploration strategy | `EpsilonGreedyExponentialDecay(1.0, 0.003)` |
| Learning algorithm | `QLearning` |
| Learning rate | `0.2` |
| Discount factor | `0.95` |

The scheduler registers observations, collects actions, applies the environment dynamics, builds experiences from the resulting rewards, and updates the independent policies.

The Q-learning update performed by each agent follows:

$$
Q_{t+1}(s,a)=Q_t(s,a)+\alpha\Bigl(r_t+\gamma \max_{a'}Q_t(s',a')-Q_t(s,a)\Bigr)
$$

where $\alpha$ is the learning rate and $\gamma$ is the discount factor.


## Reward models

Let $\bar{r}_i$ denote the raw reward computed for agent $i$, $r_i$ its final learning reward, and $N$ the number of agents.

### Fully Cooperative Reward

`FullyCooperativeReward` gives every agent the average raw reward:

$$
r_i = \frac{1}{N}\sum_{j=1}^{N}\bar{r}_j
$$

This makes the reward signal identical for every agent during the current step.

### Mixed Reward

`MixedReward` preserves the individual outcome:

$$
r_i = \bar{r}_i
$$

This model is the most directly connected to each agent's own resource request and distance penalty.

### Fair Mixed Reward

`FairMixedReward` combines the individual raw reward with the minimum raw reward across agents:

$$
r_i = (1-\delta)\bar{r}_i + \delta\min_j\bar{r}_j
$$

where $\delta \in [0,1]$ is the equity parameter. The launcher uses $\delta = 0.5$. Increasing $\delta$ gives more weight to the least-rewarded agent.

### Logistical Reward

`LogisticalRewardModel` scales collection rewards when several agents request a unit whose stock is limited. For a collection event, the availability factor is:

$$
f_i = \min\left(1,\frac{\text{available stock}}{\text{number of requesters}}\right)^c
$$

where $c$ is the logistical coefficient. The launcher uses $c = 1.0$. Distance penalties are preserved while collection rewards are multiplied by this factor.

## Default event rewards

Reward models transform the raw rewards generated by environment reaction events. Let $\rho(e)$ denote the default reward associated with an event $e$. The main event types are:

- **CollectResourceEvent2D**: generated when an agent successfully obtains a resource from a production unit. The reward is:

$$
\rho(e_{\text{collect}}) \in \{0, 3, 5, 30\}
$$

depending on the resource type collected. Resource values are intentionally imbalanced. High-value resources are available in limited quantities, creating competition between agents.

- **DistancePenaltyEvent**: generated whenever an agent requests a production unit. The reward is negative and proportional to the travelled distance:

$$
\rho(e_{\text{distance}}) < 0
$$

In the default scenario configuration, the penalty is `0.5` per spatial unit and cannot be lower than `-1.5`.

Reward-model implementations transform these raw event rewards into the final learning reward received by each agent.

## Simulation lifecycle

`SchedulerCollectingResource` extends `MLKScheduler` and configures the following lifecycle:

1. Launch the environment and the number of agents defined by the scenario.
2. Initialize production units, stocks, and agent positions.
3. Compute observations and request one action from each agent.
4. Group resource requests by production unit.
5. Process stock allocation and create collection and distance reaction events.
6. Convert reaction events into rewards using the selected reward model.
7. Build and collect experiences for each agent.
8. Update the independent Q-learning policies.
9. End the episode after 30 steps.
10. Evaluate the episode and continue until the simulation limit is reached.

The current scheduler configuration is:

| Parameter | Value |
|---|---:|
| Episode duration | `30` steps |
| Maximum episodes | `5000` |
| Display starts after | `500` episodes |
| Display interval | `100` episodes |
| Displayed episodes | `1` |
| Display pause | `10` |

## Evaluation and results

`CollectingResourceEnvEvaluator` records three episode measures:

- **TotalReward** — the sum of rewards generated by all reaction events.
- **LowestAgentReward** — the smallest cumulative reward among the agents.
- **NumberOfResources** — the number of `CollectResourceEvent2D` events recorded during the episode.

The figures below show representative final policies for the reward-model variants. They are stored beside this README in `figures/` and are copied to the runtime classpath by Gradle.

### Results 

For the experiments presented below, each reward model was evaluated using ten different random seeds. Reported performance curves use the median across all runs. Shaded areas correspond to the interval between the first and third quartiles.

To improve readability, the plotted values are smoothed using a moving-average window of 100 episodes.

The figures below compare the four reward models on `ScenarioSpatial5`. Green corresponds to Mixed Reward, blue to Fully Cooperative Reward, red to Fair Mixed Reward, and orange to Logistical Reward.

#### Total reward

![Total reward](figures/collectingressource_total.png)

The Fully Cooperative reward typically achieves the highest total reward because every agent directly optimizes the collective objective. Logistical Reward generally ranks second by discouraging excessive competition for the same production unit. Mixed and Fair Mixed rewards often produce lower collective performance because agents tend to compete for the highest-value resources.

#### Lowest agent reward

![Lowest Agent Reward](figures/collectingressource_lowest.png)


The Fully Cooperative model tends to produce the lowest value for the worst-performing agent. Since all agents optimize collective performance, one agent can repeatedly collect a less valuable resource when that improves total system reward.

Mixed and Fair Mixed rewards exhibit more balanced individual outcomes. Agents have no incentive to voluntarily assume a low-performing role, which tends to reduce reward disparities.

With the Logistical reward model, one agent often specializes on a secondary resource while the remaining agents compete for the highest-value resource, producing intermediate fairness results.

#### Number of collected resources

![Number of collected resources](figures/collectingressource_nbResources.png)

The Fully Cooperative reward generally achieves the largest number of collected resources because agents learn to reduce competition and distribute themselves across available production units.

Mixed and Fair Mixed rewards lead to stronger competition and therefore fewer collected resources. The Logistical reward partially mitigates this effect by penalizing overcrowded production units.

## Discussion of the equity parameter

The `FairMixedReward` parameter $\delta$ controls how strongly the least-rewarded agent influences every agent's reward:

- $\delta = 0$ is equivalent to individual mixed rewards;
- intermediate values combine individual and minimum rewards;
- $\delta = 1$ gives every agent the current minimum raw reward.

In this experiment, `FairMixedReward` produces results similar to those obtained with `MixedReward`. The difference between the two models is that `FairMixedReward` penalizes an agent proportionally to the difference between its raw reward and the lowest raw reward among all agents.

However, the behavior emerging with `MixedReward` already tends to balance the agents' rewards. Consequently, adding the equity term does not substantially change the learned behavior.

Increasing $\delta$ nevertheless makes learning more difficult because the final reward becomes less directly correlated with the individual agent's actions. As $\delta$ increases, a larger part of each agent's reward depends on the outcome of the least-rewarded agent.

## Configuration and reproducibility

The main parameters are defined in source rather than in the launcher menu:

- environment dimensions and agent creation: `LauncherCollectingResource`;
- unit positions, base prices, agent positions, and distance penalty: `ScenarioSpatial5`;
- episode and simulation limits: `SchedulerCollectingResource`;
- policy, exploration, learning rate, and discount factor: `CollectingResourceAgent`;
- reward transformation: the selected reward-model implementation.

For comparable runs, keep the launcher, scenario, scheduler, and random-seed configuration unchanged. The four launchers are intended to be compared under the same scenario and scheduler settings.

## Adding a new launcher

To add another collecting-resource reward variant:

1. Create a concrete `MLKLauncher` subclass of `LauncherCollectingResource` in `marlkit.collectingresource.launchers`.
2. Implement `getRewardModel()` and `getScenario()`.
3. Add a public static `main(String[] args)` method.
4. Add runtime launcher metadata with a unique title and README heading anchor.
5. Add a matching `###` section to this README.
6. Run the launcher catalog and resource packaging tests.

Example:

```java
@LauncherMetadata(
    title = "My Reward Variant",
    documentationAnchor = "my-reward-variant")
public class LauncherMyReward extends LauncherCollectingResource {
    // reward model, scenario, and main method
}
```

No catalog or menu list needs to be edited. The generic catalog discovers the annotated class automatically.
